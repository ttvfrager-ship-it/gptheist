# Runtime retention audit

The change manages retention at the `PaperStore.write` transaction boundary. It does not change strategy thresholds, exit plans, account sizing, discovery cadence or quote cadence. No existing account file was reset or deleted. Production Railway state and process metrics were not accessible in this workspace.

## Candidate and data safety behavior

Lifecycle is explicit through `candidateLifecycle`: DISCOVERED → OBSERVING → QUALIFIED / REJECTED / EXPIRED. Permanently rejected candidates lose watchlist and observation state immediately on the next successful state transaction. Temporary traction/momentum failures remain eligible only until the original launch timestamp plus the existing maximum launch age. Repeated discovery does not extend that deadline. Dedup rows have the same deadline. Open-position records and their saved plans never enter eviction.

The persisted head and validated event chronology preserve replay protection after dedup expiry. A previously traded launch still within its eligibility window retains an `archivedClosed` tombstone even after its full trade is archived. Historical launches cannot become fresh simply because a cache was evicted. Discovery cadence, source chronology classification and trading gates remain in place.

Closed trade archival preserves full objects, raw quotes, plans and exit evidence. Lifetime performance retains wins/losses, win rate, gross profit/loss, net P&L, expectancy, holding time, profit factor, drawdown, fees, slippage and gas. Realized P&L uses an ordered prefix accumulator to preserve the original floating-point addition order. Daily-loss and strategy loss-streak decisions retain their original inputs in compact form. Strategy validation retains lifetime per-strategy counters. Distribution/research breakdowns explicitly describe the recent resident sample; full distributions remain reconstructible from disk.

Archive files are synced before the atomically renamed state snapshot commits their pointers. Failed transactions leave the previous account intact; any unreferenced archive file is audit evidence rather than part of the committed trade-page chain. Nothing removes persisted archives. A large legacy `state.json` must still be parsed once during initial migration; subsequent resident state and trade-page reads are bounded. Permanent archives require Railway persistent storage, as the existing paper account already does.

## Dashboard, quotes, logging and cleanup

Dashboard activity shows 200 events; candidates show only active observation identities; recent rejections show at most 25. Recent closed trades show at most 100. The older-trades control reads `/api/paper/trades`, follows a single persisted cursor and replaces its page instead of accumulating browser history. Equity charts show the 250 retained samples while account peak/drawdown statistics cover lifetime history.

Open positions already replace current quote/diagnostics/last-successful quote rather than appending every refresh. Retention keeps their current quote, entry quote, last success, peak, MFE/MAE and management state intact. Intermediate raw laboratory quote frames persist immediately, then leave resident activity. Quote/traction sample arrays use existing strategy windows.

No per-candidate timer, event subscription, listener or RPC watcher exists. Discovery and monitor timers have close/reset cleanup and guarded initialization. The new five-minute memory interval is unref'ed and cleared on close; it is independent of stalled scans. HTTP RPC (12s), USD (8s) and social (8s) abort timers clear in finally. RPC retry sleep resolves after bounded retries. Monitor promises remove themselves in finally. Shutdown waits for work and clears retry/tape references. Browser fixed page listeners/observers release on page teardown; replaced row nodes carry only bounded current-view closures.

No logs are buffered in RAM. Production retains meaningful trade/control messages, aggregates sell failures by reason per reporting batch and emits one scan summary rather than unchanged per-token research/rejection messages. Full underlying audit events remain on disk. Memory diagnostics emit one line every 300,000ms with rss, heapUsed, heapTotal, external, arrayBuffers, collection counts and service timer/in-flight/retry/tape counts.

## Validation and memory measurements

Reproduce the retention soak with `npm run build && node --expose-gc scripts/soak-retention.mjs`. It runs the actual V4 observation pipeline and retention through 12,000 discovery cycles at unchanged 4s chronology (13.33 simulated hours), asserts collection plateau and checks post-GC retained heap growth. The test suite also runs 20,000 rejection cycles.

Railway before: user-reported 500–800 MB RSS and crashes after hours; no production heap capture available. Local simulation before warm-up: 79.66 MB RSS, 11.12 MB heap. Settled checkpoints at cycles 2,000–11,999: heap 12.78–12.8 MB; final RSS 208.69 MB. RSS takes allocator steps (146 MB then about 209–211 MB); it is not interchangeable with retained heap. Collection counts stay exactly 75 active candidates, 75 candidate samples, 76 dedup records, 200 activity events, 250 equity records and zero positions/trades/quote records for this no-entry observation workload. These are workload-specific counts, not universal production limits. Closed trades and quotes are separately tested across archival/restart and expiry.

The saved soak result file records the reproducible simulation, not a Railway RAM guarantee. Real production memory depends on launch density, source-window size, open positions and individual RPC payloads. The relevant result is that retained state no longer scales with total uptime or total lifetime discovered launches/trades.
